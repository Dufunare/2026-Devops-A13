一、项目定位
本实践项目以四篇构建系统研究论文为需求来源，将论文中的研究原型拆分为四个可独立开发、可通过接口协同的微服务。学生在持续增加需求、处理集成故障和发布平台的过程中，学习 Git 协作、持续集成、容器化、契约测试、持续部署、可观测性、故障恢复和质量门禁等 DevOps 核心实践。
最终平台接收一个软件仓库和提交范围，完成以下闭环：
项目仓库与提交范围
    ↓
DRAFT：生成并迭代修复 Dockerfile，使项目可构建
    ↓
BuildChecker：通过 clean build 建立真实依赖基线并检测错误
    ↓
EChecker：跨提交增量更新依赖图并检测新引入或消除的错误
    ↓
MDFixer：修复缺失依赖并生成 Git patch
    ↓
重新构建、测试和检测；验证通过后输出镜像、报告与补丁
1.1 两个重要边界
ICSE/DRAFT 所实现的“自动构建”，具体指自动生成并迭代修复 Dockerfile，直至项目能够在镜像中成功构建，而不是替代所有类型的构建系统。
ASE/MDFixer 只自动修复缺失依赖（Missing Dependency，MD）。冗余依赖（Redundant Dependency，RD）由检测服务报告，但不进入自动修复流水线。
1.2 A/B大组的关系
A组负责构建依赖错误的全量检测与增量检测：TSE/BuildChecker、ISSTA/EChecker。
B组负责构建环境生成与缺失依赖修复：ICSE/DRAFT、ASE/MDFixer。
A、B不是两套平行平台。四个服务必须按统一接口连接，形成“自动构建—全量检测—增量检测—自动修复—重新验证”的完整平台。
鼓楼校区和苏州校区分别实现一套平台，共用需求、接口规范、测试项目和隐藏测试集。
二、平台级需求
2.1 功能需求
P-01：支持提交仓库地址、commit或提交区间、构建命令和验证命令。
P-02：自动产生可复现的容器化构建环境，并保存 Dockerfile、镜像标识和完整日志。
P-03：对基线提交执行 clean build，生成实际依赖图与声明依赖图。
P-04：比较两类依赖图，报告缺失依赖与冗余依赖，并给出可解释证据。
P-05：在连续提交之间增量更新实际依赖图，识别当前提交引入或消除的依赖错误。
P-06：对缺失依赖生成 Makefile 补丁，自动执行构建、测试和重新检测。
P-07：修复验证失败时拒绝补丁并回滚，不能破坏原始仓库。
P-08：输出最终 Dockerfile、镜像、依赖图、错误报告、修复补丁和实验指标。
2.2 工程需求
P-09：四个服务均同时提供 CLI 和 REST API，核心算法不得与 Web 框架强耦合。
P-10：耗时操作采用异步任务模型，统一使用 job_id 查询状态。
P-11：服务之间只传递结构化元数据和 artifact URI，不直接传输大型日志、镜像和依赖图。
P-12：所有任务具有超时、资源限制、幂等键和可重试策略。
P-13：所有服务使用统一 trace_id、日志字段、错误码和版本号。
P-14：接口变更必须更新契约版本，并通过消费者契约测试后才能合并。
P-15：每个服务必须具备单元测试、集成测试、容器构建和自动化 CI。
P-16：平台能够在指定环境中一键部署，并运行端到端隐藏测试。
三、服务一：ICSE/DRAFT自动构建服务
3.1 服务目标与接口
输入包括仓库地址、commit、目标构建命令、可选验证命令、LLM配置和最大迭代次数。输出包括最终 Dockerfile、镜像 ID、每轮构建日志、Dockerfile diff、错误定位记录和最终验证结果。
建议核心接口：
POST /v1/dockerfile-jobs
GET  /v1/jobs/{job_id}
GET  /v1/jobs/{job_id}/artifacts
3.2 需求与实现指导
D-01：提取项目上下文
最低要求读取 README、构建说明、语言信息、Makefile/CMakeLists.txt 和依赖清单。论文主要使用 README，课程提高要求可增加对构建文件、CI配置和历史构建命令的分析。
实现建议：先以规则判断项目类型并提取关键片段，再将裁剪后的上下文交给 LLM；必须限制上下文长度并记录选取了哪些文件，避免直接把整个仓库发送给模型。
D-02：生成初始Dockerfile
根据项目上下文构造提示，生成一个或多个初始 Dockerfile 候选。LLM调用应封装为统一接口：
LLMProvider.generate(prompt) -> DockerfileCandidate[]
API Key 只通过密钥管理或环境变量注入，严禁写入代码、镜像、日志和配置仓库。
D-03：执行容器构建
每次构建必须保存 Dockerfile 版本、stdout/stderr、exit code、耗时、image ID和末尾日志摘要。构建任务异步执行，并设置 CPU、内存、磁盘、网络和时间限制。
D-04：定位构建错误
优先匹配 error、unknown、missing、no such file or directory、failed to execute、file not found、unable to locate package、no matching distribution found 等典型关键词；规则无法定位时，再由 LLM 分析日志末尾片段。
D-05：生成修复候选
实现两类提示策略：
Error-driven：Dockerfile与错误日志。
Context-driven：项目上下文、Dockerfile与错误日志。
每种策略最多生成3个候选，保存候选来源和生成轮次。
D-06：候选选择
依次应用：排除历史重复候选；优先多数相同候选；检查修改与错误关键词是否匹配；前三项不能决定时再由 LLM 选择。选择过程必须可追踪，不能只保存最终结果。
D-07：迭代与终止
满足以下任一条件终止：构建成功且验证命令通过；达到最大轮次；多轮产生相同 Dockerfile；任务超时或超出资源限制。失败任务必须给出明确终止原因。
D-08：Dockerfile优化（提高要求）
在正确构建基础上，再考虑更小的基础镜像、合并 RUN 命令、减少安装包、多阶段构建和自动生成 .dockerignore。优化前后必须再次验证功能，不得用镜像大小换取不可复现性。
3.3 验收标准
至少完成3个指定项目的 Dockerfile 生成。
至少展示一个“初始构建失败—自动定位—自动修改—成功构建”的完整案例。
输出每轮 Dockerfile diff、错误摘要和选择理由。
最终镜像内的目标程序通过指定验证命令。
相同幂等键重复提交不会创建失控的重复构建。
四、服务二：TSE/BuildChecker全量依赖检测服务
4.1 服务目标与接口
输入包括 DRAFT 提供的可构建环境、仓库与commit、clean build命令和项目根目录。输出包括实际依赖图、声明依赖图、MD/RD报告以及每条错误的证据。
建议核心接口：
POST /v1/full-check-jobs
GET  /v1/jobs/{job_id}
4.2 需求与实现指导
T-01：跟踪clean build
论文使用 ptrace 跟踪 GNU Make及其子进程的文件操作。课程MVP可以先使用：
strace -ff -e trace=%file,%process make
至少识别进程及子进程、当前工作目录、read/open/openat、create/write、rename/delete和execve。一个编译或链接进程生成目标文件时，将该进程读取的项目文件记录为目标的实际依赖。
T-02：路径与进程归一化
统一处理相对路径、绝对路径、符号链接、构建目录、源码目录和子进程继承关系。系统头文件可以过滤，但项目内部生成文件不能简单排除。建议先形成独立的 PathNormalizer 与 ProcessTracker，再构建依赖图。
T-03：构建实际依赖图
统一边结构示例：
{
  "target": "src/a.o",
  "dependency": "include/a.h",
  "kind": "ACTUAL",
  "evidence": {
    "source": "system_call",
    "process": 1024,
    "operation": "openat"
  }
}
T-04：提取声明依赖图
优先利用 GNU Make内部数据库，而不是自行完整解释 Makefile：
make -p
解析目标、前置依赖、宏展开结果、隐式规则和 .PHONY 信息。解析器的原始输出与标准化结果都应保存，以便定位误报。
T-05：检测错误
对同一目标比较：Actual - Declared = Missing Dependency，Declared - Actual = Redundant Dependency。错误报告包括 target、dependency、error type、commit、actual evidence、declared location和detector version。
T-06：生成可解释报告
报告不仅给出错误数量，还要回答：哪个编译进程读取了依赖文件；Makefile中目标声明是什么；两者为什么不一致；路径是否经过归一化或过滤。
4.3 验收标准
准备人工故障项目：main.c实际包含config.h，但main.o未声明config.h；同时声明一个未使用的unused.h。系统必须识别config.h为MD、unused.h为RD，不能误报系统头文件，连续运行3次结果一致。提高要求是在2—3个论文案例项目上与论文工具或人工结果进行对比。
五、服务三：ISSTA/EChecker增量检测服务
5.1 服务目标与接口
输入包括 TSE 建立的历史实际依赖图、parent commit、target commit、构建命令、环境信息和历史构建命令。输出包括更新后的实际依赖图、当前声明图、当前提交引入或消除的MD/RD、与全量检测的差异和增量检测耗时。
建议核心接口：
POST /v1/incremental-check-jobs
GET  /v1/jobs/{job_id}
5.2 需求与实现指导
I-01：应用提交并跟踪增量构建
checkout parent commit并载入历史依赖图；切换或应用target commit；跟踪incremental build；更新本次真正重建目标的实际依赖。应保留提交切换、工作区清理和构建命令的完整记录。
I-02：分析预处理指令变化
比较提交前后的#include "a.h"和#include <b.h>等指令。如果源文件增加或删除include，应更新所有依赖该源文件的目标，不能只依赖本次实际执行的编译命令。
I-03：分析文件变化
对新增、删除和重命名的 C/C++ 文件更新依赖图。对新增源文件可调用编译器获取依赖：
gcc -MM source.c
重命名需要更新图中路径；删除文件需要移除相关节点和边，并检查是否产生新的声明错误。
I-04：分析构建命令变化
获得目标在提交前后的构建命令：
make -n -B --debug=basic
如果目标的构建命令发生变化，但 Make 没有重建该目标，则单独重建并跟踪，例如make target.o。这是 EChecker区别于普通增量构建监控的关键要求。
I-05：合并实际依赖图
合并历史clean build图、当前增量跟踪结果、include变化、文件新增/删除/重命名以及构建命令变化后的单独重建结果。每条边应带来源标记，便于解释和排错。
I-06：重新提取声明图并检测
在target commit运行make -p取得当前声明图，处理.PHONY后与更新后的实际图比较。必须同时输出“当前错误集合”和“相对parent commit的错误变化”。
5.3 验收标准
至少准备三个连续提交：C0为正确基线；C1增加#include "feature.h"但不修改Makefile；C2修改编译命令或条件编译配置。C1应发现新MD；C2应识别“命令变化但目标未正常重建”；同一target commit上，EChecker结果应与TSE clean build结果一致。输出增量与全量检测耗时，但不硬性要求达到论文报告的加速倍数。
六、服务四：ASE/MDFixer缺失依赖修复服务
6.1 服务目标与接口
输入包括TSE或ISSTA产生的MD报告、Makefile、项目声明依赖图和可选LLM配置。输出包括声明风格分类、定位结果、Git patch、修复前后检测结果以及构建与测试结果。
建议核心接口：
POST /v1/repair-jobs
GET  /v1/jobs/{job_id}
6.2 需求与实现指导
F-01：解析Makefile与声明图
至少支持变量赋值、$(VAR)/${VAR}、wildcard、target-prerequisite规则、pattern rules、多行声明和.d动态依赖文件。建立由target、macro和dependency组成的声明图。
F-02：识别声明风格
依据依赖到目标的Declaration Distance Score，将项目分为：
F-03：定位错误声明
检测报告给出具体target，但Makefile中可能通过宏描述多个目标，例如$(BINS): $(SRC)。系统必须先判断目标属于哪个宏，再定位相关声明，不能简单搜索target字符串。
F-04：修复显式声明
Target style直接附加依赖；Macro style加入或创建合适宏；Hybrid style在同目录、同类型且全部有效时可考虑wildcard，否则显式枚举。修改必须保持原有缩进、换行和声明风格。
F-05：修复隐式声明
对于%.o: %.c等隐式规则，向模型提供裁剪后的Makefile或声明图、target与缺失依赖、保持原风格的约束、优先考虑.d文件的提示，以及只输出补丁的格式约束。模型输出必须通过语法和安全检查后才能应用。
F-06：验证与回滚
补丁生成后自动执行：应用patch；clean build；运行测试；重新运行BuildChecker/EChecker；确认原MD消失；比较修复前后实际依赖图；检查没有产生新的构建失败。任一验证失败即撤销补丁并记录原因。
6.3 验收标准
三种显式风格各准备一个测试项目，另准备至少一个隐式规则项目。
修复后原MD消失，Makefile原有声明风格得到保留。
clean build和测试通过。
无效或高风险LLM修改能够被拒绝并回滚。
最终输出Git patch，不直接覆盖用户仓库。
七、统一接口与数据契约
7.1 异步任务接口
建议统一任务状态：QUEUED、RUNNING、SUCCEEDED、FAILED、CANCELLED、TIMED_OUT。
7.2 统一错误结构
{
  "type": "MISSING",
  "target": "src/fzy.o",
  "dependency": "src/match.h",
  "commit": "f061893",
  "detector": "ECHECKER",
  "detector_version": "1.0.0",
  "trace_id": "trace-2026-001",
  "evidence": [
    {
      "source": "include_change",
      "file": "src/fzy.c"
    }
  ]
}
7.3 Artifact传递
大文件通过URI引用：dockerfile_uri、build_log_uri、actual_graph_uri、declared_graph_uri、error_report_uri和patch_uri。四个服务从Sprint 0开始使用模拟JSON和模拟artifact协作，不能等待上游全部完成后才开始集成。
7.4 版本与兼容性
API路径采用主版本号，例如/v1/。
JSON Schema存入公共契约仓库并由CI校验。
字段新增默认保持向后兼容；字段删除或语义变化必须提升主版本。
每个消费者为其依赖的上游接口提供契约测试。
八、两校区组织与分组
8.1 鼓楼校区：79人
鼓楼每个论文服务可拆为：核心算法小队、服务与运行环境小队、测试与集成小队。每个小队内部再明确模块负责人、测试负责人和集成联系人，角色可以按Sprint轮换。
8.2 苏州校区：175人
苏州校区适合按需求编号进行更细拆分。例如TSE可分为：构建跟踪、进程与路径归一化、实际依赖图、GNU Make数据库解析、声明图与错误检测、API与任务运行环境、测试实验与平台集成。
其他服务可参考以下拆分：
DRAFT：上下文提取、提示与模型适配、容器构建执行、日志错误定位、候选生成与选择、API与任务队列、测试与集成。
EChecker：提交与工作区管理、增量构建跟踪、include变化、文件变化、构建命令变化、依赖图合并与检测、测试与集成。
MDFixer：Makefile解析、声明图与DIS、风格分类、显式修复、隐式修复、验证回滚、API与集成。
8.3 大组内协作原则
论文服务组不是独立交作业，而是共同维护一个服务产品。
每个小队必须有独立代码目录、明确接口和可单独验收的测试。
服务组设1名集成负责人，但集成不能由一人包办；每个小队都要维护自己的契约测试。
个人贡献通过Issue、Commit、PR、Review、测试和文档记录，不以组长主观分配为唯一依据。
九、迭代式课程安排
9.1 可由教师逐步发布的故障单
“昨天升级后，相同提交被执行了两次。”要求引入幂等键和去重。
“MDFixer生成补丁后项目无法构建。”要求增加自动验证和回滚。
“A组修改错误报告字段后，B组流水线失败。”要求增加Schema版本和契约测试。
“某个构建运行40分钟仍未结束。”要求增加超时、取消和资源限制。
“无法判断失败发生在哪个服务。”要求增加统一trace ID、日志和指标。
“LLM服务临时不可用。”要求实现失败分类、有限重试和降级处理。
“批量任务耗尽磁盘。”要求增加artifact生命周期、配额和清理策略。
十、测试与验收体系
10.1 三级复现标准
基础复现：核心算法在人工故障项目上正确运行。
平台复现：四个服务完成服务化、自动测试、CI/CD和跨组集成。
提高复现：在3—5个论文项目上复现论文主要结果或趋势，并解释差异。
不要求所有学生完整重跑论文全部实验数据，以免课程退化为长时间环境配置和批量运行。
10.2 测试层次
单元测试：解析器、路径归一化、图差分、状态机和候选选择。
组件测试：每个服务使用固定fixture验证输入输出。
契约测试：验证服务提供方与消费方对JSON Schema和错误码理解一致。
集成测试：两个相邻服务通过真实artifact交接。
端到端测试：从仓库输入到Dockerfile、检测报告和修复补丁输出。
回归测试：每次修复问题后把失败样例加入自动测试集。
隐藏测试：教师提供未公开项目、异常日志和接口兼容场景。
10.3 Definition of Done
一个需求只有同时满足以下条件才算完成：代码已合并；单元和集成测试通过；接口文档已更新；容器能够构建；CI无失败；日志包含trace_id；安全扫描无阻断问题；在指定环境中能够复现；对应Issue与PR可追踪。
十一、评分建议
建议设置以下最低门槛：每名学生至少完成1个被合并的实质性PR、1次对他人PR的有效Review、1个自动化测试或故障复现记录。未达到个人门槛者不能完全共享小组得分。
十二、准备清单
提供四篇论文和每篇论文的简化讲义。
建立公共接口契约仓库、服务模板仓库和示例客户端。
准备一个最小人工故障项目和3个连续提交的增量检测项目。
为四个服务分别准备mock输入、期望输出和错误示例。
建立统一CI模板、容器资源上限和密钥使用说明。
准备公开测试集与隐藏测试集，隐藏测试覆盖错误输入、超时、重复任务和接口版本变化。
明确两个校区的代码仓库、镜像仓库、部署环境和最终演示方式。
规定Issue、PR、Review和个人贡献记录格式。
