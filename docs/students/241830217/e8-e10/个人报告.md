### E10 云服务器实测性能

来源：`work/e10-A-targetwise-241830217-20261103-150759/performance-summary.csv`。以下时间单位为**秒**，数值按 CSV 中位数四舍五入至 6 位小数；加速比为同一场景的**全量中位数 / 增量中位数**，四舍五入至 3 位。每组 5 次，合计 30 对。

| 场景 | 增量中位数 (s) | 全量中位数 (s) | 复用 / 刷新 | 全量 / 增量 |
|---|---:|---:|---:|---:|
| unchanged | 0.001690 | 0.009775 | 2 / 0 | 5.784× |
| body | 0.001668 | 0.009993 | 2 / 0 | 5.991× |
| include | 0.006521 | 0.009809 | 1 / 1 | 1.504× |
| declaration | 0.001723 | 0.009811 | 2 / 0 | 5.694× |
| flags | 0.009996 | 0.009841 | 0 / 2 | 0.985× |
| header | 0.006615 | 0.009794 | 1 / 1 | 1.480× |

- `unchanged/body/declaration` 未刷新 GCC 对象依赖，耗时中位数约 **1.7 ms**；这里的“复用”是**实际依赖图缓存复用**，不是不运行程序其他检查步骤。
- `include/header` 只刷新 `main.o`，中位数约 **6.5–6.6 ms**，在本次课堂小样例上相对全量 GCC 扫描约 **1.48–1.50×**。
- `flags` 改变影响全部目标，刷新 2 个，中位数 **0.009996 s**，略慢于全量的 **0.009841 s**（比值 **0.985×**）。**不删除不利数据，也不宣称所有场景均加速。**
- 计时覆盖扫描读取、Git HEAD / GCC 版本检查、Make 声明和 GCC `-MM` 等开销；**不等于完整 clean build 的性能**。样例规模小、重复仅 5 次、共享服务器存在噪声，不能将该比例推断至真实大型工程或 EChecker 论文。

## 6. 论文对应、适用范围与实验结论

**对应的研究思想**：EChecker 关注历史依赖图的保存、变更识别与避免无谓重检。教师子集用 `gcc -MM` + 保守缓存作教学模拟；本次个人扩展在该子集上引入**目标级依赖签名**，将本来因 `main.c` include 变化而全体刷新的行为，缩小为只刷新 `main.o`。纯 Make 声明变化重新计算 MD/RD，而不重新采集未变化的真实依赖。

**限制**：仅验证两个 GCC C 对象目标、简单本地头文件和显式 Make 规则；不支持任意 C/Make 项目、隐式规则、生成头文件、复杂工具链和 EChecker 论文的增量 syscall trace 合并。五次重复的微秒/毫秒级计时不代表大规模构建性能。

**本轮验收结论**：基于已回传的 `TEST_EXIT=0`、六阶段 `EXIT=0`、E10 30 行及 `full_graph_equal=true`、E8/E10 `BuildChecker status=SUCCEEDED`、原始 trace 文件及三个成功的 Actions 运行，**2026-11-03 的 A13/E8–E10 官方一键实验与本人逐目标扩展均已达到主要技术验收条件**。
